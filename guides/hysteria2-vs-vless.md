# Hysteria2、Vless、AnyTLS：代理协议到底该选哪个

Hysteria2 基于 UDP/QUIC，VLESS 常见配置可能使用 TCP，但节点的实际传输参数由服务端和客户端配置决定。丢包、UDP 可达性、拥塞与线路质量都会影响体验；协议名称本身不能保证速度、稳定性或抗干扰能力。可以将多种节点作为候选，在同一网络、同一时段做对照测试。

## 一、常见传输配置的差异

| 协议 / 常见节点配置 | 传输特征 | 说明 |
| --- | --- | --- |
| Hysteria2 | 基于 QUIC，使用 UDP | UDP 不可达或受限时可能无法连接；实际效果也受服务端参数和网络影响 |
| VLESS 常见 TCP 配置 | TCP；安全层与传输方式由节点配置决定 | UDP 受限时可作为对照候选，但不能据此保证一定可用或更稳定 |

传输层差异会影响节点在特定网络里的表现，但不能单凭协议名判断结果。Reality、TLS、WebSocket 等具体组合及客户端实现也会改变行为。

## 二、四个维度的对比

| 维度 | Hysteria2 | VLESS 常见 TCP 配置 |
| --- | --- | --- |
| UDP 可达性 | 依赖 UDP；被网络限制时可能无法连接 | 若节点确实使用 TCP，可用于对照测试 |
| 丢包与拥塞 | QUIC 与服务端拥塞控制参数会影响表现，不能据此保证更快 | TCP 在丢包、拥塞下也可能出现吞吐下降或延迟变化 |
| 延迟与游戏体验 | 取决于线路、节点负载和本地网络，需观察抖动与丢包 | 同样受线路和配置影响，不能仅按协议名判断 |
| 资源开销 | 受实现、配置与设备影响 | 受实现、配置与设备影响 |
| 连接特征 | 取决于具体实现与服务端配置 | Reality/TLS 等是具体配置选项，不构成可用性或隐匿性保证 |

拥塞控制行为与实现和参数有关。在带宽紧张或多人共享线路时，某个节点的高吞吐可能影响同线路的其他连接；出现这种情况应同时检查节点负载、客户端配置和网络，而不只归因于协议。

## 三、AnyTLS 又是怎么回事

**AnyTLS** 是另一种协议实现，具体传输行为、兼容性及流量特征会受服务端和客户端版本影响。不要把协议名称或宣传中的流量特征描述理解为隐匿性、抗封锁或可用性保证；遇到节点不显示时，先核对客户端版本及服务商给出的配置要求。

## 四、按场景选

* **移动网络、信号波动或丢包**：可把 UDP 与 TCP 节点都纳入测试，观察稳定性、丢包和吞吐，不预设哪种一定更好。
* **有线宽带、家用路由器**：按设备耗电、延迟和长时间运行表现实测；具体开销与实现有关。
* **校园网、公司网络、公共 WiFi**：先确认网络规则与授权范围；若某类传输不可用，再用另一种节点做对照。
* **晚高峰视频卡顿**：在相近时间段测试，记录速度、丢包和抖动，不要只看单次延迟。
* **打游戏**：优先关注实际游戏中的延迟抖动与丢包；测速结果不能替代游戏内验证。

## 五、实践中的用法

不需要纠结"哪个更好"，正确做法是：

1. **两种协议的节点都留在订阅里**，用延迟测试筛出各自最快的两三个；
2. 日常使用确认可用的节点；遇到异常时换另一种传输配置做对照，并结合日志、订阅状态和其他网络检查缩小范围，不能仅据此判断原因；
3. 客户端里把常用节点固定成策略组，切换时少点几下。

需要提醒的是，协议只是影响体验的因素之一。**同一协议下，线路质量（中转还是专线）对你的实际体验影响往往更大。** 判断线路差异的方法见[机场套餐怎么选](plan-choosing-guide.html)。

## 六、症状对照：线索而非确诊

| 症状 | 优先怀疑 |
| --- | --- |
| 只有 UDP 类节点超时，另一种配置正常 | 可能与 UDP 可达性、节点状态或服务端配置有关 |
| 视频能播但游戏频繁掉线 | 当前节点的延迟抖动过大 |
| 刚开始很快，几分钟后掉速 | 可能与节点负载、网络拥塞、配置或服务端策略有关；对照其他节点和时段 |
| 不同网站表现差异较大 | 检查分流规则、域名解析、目标站点和网络条件，不能仅按协议判断 |
